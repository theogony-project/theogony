# E8.5 — Memory Lifecycle (`OneirosWorker`) — Daedalus Design Brief

Brief from Hesiod to Daedalus, 2026-04-19. Companion to Plan §2.7, §4.3, §4.4, §5 E8.5 (S–M); follows merged Etappe E9 (PR #23) and the Production-Readiness Cluster (PR #24).

---

## Why a design brief, not an implementation brief

E7/E8/E9 each had a clean architectural shape Hesiod could hand straight to Talos: an interface, a layer split, a wiring decision, done. E8.5 is different. The `OneirosWorker` is the Plan §4.3 write-back loop personified, and its shape touches three open architectural questions at once:

1. **Vitality formula evolution.** Plan §8 explicitly notes vitality is "kept; defaults are heuristic and PHX-0009 records empirical tuning is needed". The worker's `_tick()` recomputes vitality. If we hard-code the computation in the worker, every PHX-0009 iteration drags through the worker. If we abstract it behind an interface today, we anticipate a refactor that may never need to happen.
2. **Atomicity vs latency.** PHX-0048 (deferred to Gen 2) catalogs the read-modify-write race between `OneirosWorker._tick()` and `RelevanceTracker.bump()`. The "deferred" verdict was correct when no concurrent writer existed; E8.5 *creates* the concurrent writer. The race becomes live, and the question reopens.
3. **Tick-loop concurrency model.** A long-running asyncio task, FastAPI lifespan ownership, IngestionPipeline writes, RelevanceTracker bumps, and a once-per-N-seconds full-store sweep — none of those are individually surprising, but the composition has at least four subtle interactions worth specifying before code lands.

Talos is excellent at executing a settled design and surfacing concrete blockers at PR time. Talos is not the right person to *make* the architectural choices above, because each one requires reading the Phoenix backlog, the §8 preservation audit, and the §9 challenged-decisions audit and weighing them against each other. That is Daedalus's surface.

This brief asks Daedalus for a **design PR** (Plan-patches + optional new PHX tickets + optional ARCHITECTURE.md note). No code in `src/`. The output is a Plan-patch PR that Hesiod then translates into a Talos implementation brief.

## What is already settled — do NOT re-open

These are decisions that have lived through Hesiod review, are carried in code or doc, and are NOT subjects of this brief:

- **Plan §4.4 main-loop shape.** `_tick()` between `asyncio.sleep` calls, `try/except CancelledError` for clean shutdown. The 5-second graceful-shutdown budget is enforced by the FastAPI lifespan (E9, `api/app.py:lifespan`). Do not redesign the loop skeleton.
- **`vitality()` formula already lives in `core/model.py`.** It is a weighted sum: `0.4 * confidence + 0.25 * relevance + 0.2 * connectivity + 0.15 * freshness`. PHX-0009 (Vitality function tuning) records that the weights are heuristic and need empirical tuning. Daedalus does NOT propose new weights here — that is PHX-0009's job. Daedalus DOES decide whether the worker computes vitality via `node.scores.vitality()` or replicates the formula inline (and why).
- **`OneirosTickReport` schema is frozen** (`reporting/models.py`). `nodes_evaluated`, `nodes_promoted`, `nodes_degraded`, `vitality: VitalityShift`, `duration_s`. Do not propose new fields. (If you find a field is *missing*, file a separate PHX ticket; do not fold it into this design.)
- **Retention cap = 100, wired via `Settings.report.oneiros_tick_retention`.** `RunReportWriter` already handles cap enforcement. The worker just calls `writer.write(report)`; rotation is not the worker's concern.
- **E9's lifespan slot exists and is conditional** (`app.state.oneiros = None` placeholder; if-not-None dispatch in startup/shutdown). E8.5 fills the slot — i.e. constructs an `OneirosWorker` at lifespan startup and assigns it. Do not redesign the lifespan-wiring contract.
- **`RelevanceTracker.bump(node_id)` (E8) is the read-side write-back.** It is in production. The worker is the write-side write-back. Do NOT refactor the relevance tracker as part of E8.5.
- **No semantic association in Gen 1.** Plan §2.7: "No semantic association beyond the trivial co-occurrence already produced by extraction. PHX-0004 (Crystallized Inference) is deferred." E8.5 does NOT introduce associative behavior.
- **Tick interval default = 60s.** Plan §4.3. Tunability is a design question (Q1 below).

## Design questions Daedalus must answer

Each question has Hesiod's leaning ("cheap-defensible default") so Daedalus can confirm, refine, or refute. The Daedalus output should treat each Q as a mini-Advocate/Skeptic/Counterview round and land on a recommendation.

### Q1 — Tick interval mechanism and bounds

**Question.** Plan §4.3 fixes the default at 60 s. Should this be (a) a hard-coded constant in the worker, (b) a `Settings.oneiros.tick_interval_s: float = 60.0` field, or (c) a constructor parameter with a `Settings`-derived default?

**Why it matters.** The integration test pattern in Plan §5 E8.5 explicitly uses a 0.1-s tick interval (`Risks: Async-clock drift in tests. Mitigation: ... integration test uses a 0.1-s tick interval`). That requires runtime tunability. Settings vs constructor parameter is the only real choice; the question is which surface a future operator/test author goes through.

**Hesiod's leaning.** (c) constructor parameter with `Settings.oneiros.tick_interval_s` as the production source. Reason: tests can pass `tick_interval_s=0.1` directly without monkeypatching settings; the lifespan reads from `Settings.oneiros` in production. This matches the pattern the rest of the codebase already uses (`AnswerSynthesizer(llm, prompt_path=...)` etc.).

**Daedalus output.** Confirm or refute. If (b), explain why tests should monkeypatch settings rather than pass parameters.

### Q2 — Promotion and degradation criteria

**Question.** Plan §4.3 says "promote what passes the threshold". What threshold? In which direction (vitality only, or also `relevance` and `connectivity` independently)? Is degradation symmetrical, or asymmetrical (require lower threshold + a minimum age in EPHEMERA)?

**Why it matters.** This is the actual policy of the Memory layer. Two behaviors are possible:
- **Single-threshold, symmetric.** `vitality >= 0.7 → EPHEMERA→MNEME; vitality <= 0.3 → MNEME→EPHEMERA`. Easy. Risk: a node that hovers at 0.3 thrashes between layers each tick.
- **Hysteresis, asymmetric.** `vitality >= 0.7` to promote; `vitality <= 0.2` AND `last_accessed > 7 days ago` to degrade. Harder. Avoids thrashing and gives recently-touched nodes a grace period.

**Hesiod's leaning.** Hysteresis. Promotion at `vitality >= 0.7`; degradation at `vitality <= 0.25` AND `last_accessed > 7 * 86400 s`. The grace period is the cheap defensible way to keep the demo well-behaved without filing a "we observed thrashing" PHX after the fact. Defaults exposed as `Settings.oneiros.promote_threshold`, `degrade_threshold`, `degrade_min_idle_days`.

**Daedalus output.** Confirm hysteresis or refute (with a plausible thrashing-avoidance argument that the simpler version satisfies). If hysteresis, fix the three defaults.

### Q3 — Connectivity recomputation formula

**Question.** Plan §4.3 says connectivity is recomputed "from edge count". `NodeScores.connectivity` is a `[0, 1]`-ranged float. What function turns "this node has 12 outbound + inbound edges" into `[0, 1]`?

**Hesiod's leaning.** `connectivity = min(1.0, edge_count / 20.0)`. Linear cap at 20 edges = full connectivity credit. Reason: 20 is the Plan §3.1a HNSW vector index neighbor cap (so it matches the "this node is interesting in graph terms" intuition the rest of the system already encodes); linear (not log) keeps the recomputation honest about the marginal value of an additional edge until saturation. Above 20, additional edges may signal a hub but offer diminishing recall benefit for the demo.

**Daedalus output.** Confirm linear-cap-at-20 or refute (e.g. `min(1.0, log1p(edge_count) / log1p(20))` if log-scale matches the qualitative behavior of `vitality()` better; the trade-off is "do we want a node with 5 edges to be at 0.25 connectivity (linear) or at ~0.6 connectivity (log)?"). Daedalus picks; the answer goes into the §5 E8.5 block as pseudo-code.

### Q4 — Freshness decay function

**Question.** `NodeScores.freshness` is `[0, 1]`-ranged. It is set to `1.0` on `RelevanceTracker.bump()` (E8) and decays over time when the worker recomputes. What decay function?

**Hesiod's leaning.** `freshness = max(0.0, 1.0 - (now - last_accessed).total_seconds() / (30 * 86400))`. 30-day linear decay to zero. Reason: matches the rough "MNEME promotion is durable, EPHEMERA decays away over the order of weeks" feel that the Plan §1 demo language hints at, and 30 days is the same number the §3.4 manual-resolution window uses (consistency, not coincidence). `Settings.oneiros.freshness_horizon_days = 30`.

**Daedalus output.** Confirm 30-day linear, or propose half-life-style exponential (e.g. `exp(-days_since_access / 14)`, half-life 14 days). The exponential variant is mathematically prettier but requires a constant `tau` whose semantics are harder to explain to a future operator. Daedalus chooses for the demo defensibility.

### Q5 — Atomicity of `update_scores` (PHX-0048 reopen)

**Question.** PHX-0048 ("Neo4jKnowledgeStore.update_scores collapses to one round-trip via Cypher COALESCE", deferred Gen 2) has a "race-condition note (added 2026-04-19, post-E8 reconciliation)" specifically calling out E8.5 as the moment the race becomes live. Does E8.5 ship with the two-roundtrip pattern (and document the race as acceptable for the demo's ≤2000-node retention surface), or does E8.5 reopen PHX-0048 and ship the atomic Cypher COALESCE?

**Why it matters.** The two-roundtrip read-modify-write pattern in `RelevanceTracker.bump()` AND the same pattern Daedalus is about to design into `OneirosWorker._tick()` will race against each other. Worst case: a `bump()` after a `_tick()` read but before the `_tick()` write loses the bump. Best case: the next tick fixes it. The question is whether "the next tick fixes it" is acceptable, or whether the operator-visible behavior of "I queried, it bumped, but the metric never moved" is a demo-killing surprise.

**Hesiod's leaning, weakly.** Defer PHX-0048 to Gen 2 still, ship E8.5 with the two-roundtrip pattern, BUT document the race in the worker docstring AND add one PHX-0048-blocked test that asserts the convergence behavior (`bump() during tick → tick completes → next tick reflects the bumped value`). Reason: the actual cost of a lost bump in Gen 1 is one tick-interval-of-staleness on one node's relevance score; the user will not see this. The PHX-0009 weights are still heuristic; locking the formula into Cypher today is premature.

**Counter-argument Daedalus should weigh.** If PHX-0048 is "easy enough now" (Daedalus's call, not Hesiod's — Daedalus has the deeper Cypher feel), then folding it into E8.5 means the worker ships with one fewer documented race. The cost is one new acceptance criterion in PHX-0048 (cross-version contract test) and the freezing of the vitality formula's *shape* (weighted sum with parameters), even if the weights themselves stay tunable via PHX-0009.

**Daedalus output.** Pick. Either (a) defer PHX-0048 + document the race + ship the convergence test, OR (b) reopen PHX-0048, fold it into E8.5, define the parameter shape now. If (b), file the parameter-shape decision as a PHX-0048 reopen note and provide the Cypher pseudo-code.

### Q6 — Concurrency model with `IngestionPipeline` and `RelevanceTracker`

**Question.** The worker runs concurrent to (i) `IngestionPipeline.run` (writes new nodes via `batch_upsert_*`), (ii) `QueryPipeline.ask` (reads + triggers `RelevanceTracker.bump`), and (iii) `RelevanceTracker.bump` itself. What is the worker's stance on each of these three?

**Race scenarios and Hesiod's leaning.**

| Scenario | Hesiod's stance |
|---|---|
| Ingestion adds a new node mid-tick | Acceptable. Worker iterates over the snapshot it read at tick start; new nodes wait for the next tick. Document this. |
| RelevanceTracker.bump during tick (same node) | Q5 above. Convergence-on-next-tick. |
| Two ticks overlap (long tick, short interval) | Forbid. The worker enforces a strict serial loop: `await self._tick(); await asyncio.sleep(interval)`. Never `asyncio.create_task(self._tick())`. |
| Worker reads a node mid-bump | Acceptable. Read returns either the pre-bump or post-bump value. Both are valid lifecycle inputs. |

**Daedalus output.** Confirm the table or replace specific rows. If Daedalus proposes any kind of explicit lock or version-counter on the store, file it as a separate PHX ticket — Hesiod is not staffing E8.5 for store-side concurrency machinery.

### Q7 — Test strategy: fast clock idiom

**Question.** Plan §5 E8.5 risks bullet specifies "`asyncio.sleep` is monkeypatched in unit tests; integration test uses a 0.1-s tick interval". Two idioms are common in the asyncio-Python world for this:

- **Idiom A: `monkeypatch.setattr("asyncio.sleep", AsyncMock(return_value=None))`** + manually drive the loop: `asyncio.create_task(worker.run())`, `await asyncio.sleep(0)` to yield, count ticks observed via the report writer.
- **Idiom B: `asyncio.get_event_loop().advance_time(...)`** style time-travel via `pytest-asyncio` fixtures (a more fragile pattern; not all asyncio runtimes support it).

**Hesiod's leaning.** Idiom A. Reason: it works on every supported Python (3.11/3.12/3.13) without optional plugins, it makes the test obviously deterministic ("after N forced yields we have N reports written"), and it doesn't introduce a clock dependency that future asyncio refactors might break. The integration test (one, not many) uses a real 0.1-s interval and asserts wall-clock-bounded behavior.

**Daedalus output.** Confirm Idiom A (and provide a one-paragraph pattern recipe Talos can copy), or propose Idiom B with a test that survives a Python 3.13 → 3.14 upgrade.

### Q8 — `VitalityShift` computation: full sweep vs sample

**Question.** `OneirosTickReport.vitality: VitalityShift` requires `nodes_evaluated`, `mean_vitality_before`, `mean_vitality_after`, `median_shift`. Computing these on every tick over the entire EPHEMERA layer requires reading every node's pre-tick vitality and tracking each delta. Full-sweep vs sample?

**Hesiod's leaning.** Full sweep for Gen 1. Reason: at the demo-target ≤2000 nodes, full sweep is two `list[float]` aggregations and a sort for the median — total cost <50 ms client-side, dominated by the Cypher read which is a single Bolt round-trip via `KnowledgeStore.list_layer(EPHEMERA)` (or whatever the equivalent slim-projection API is — see Q9). Sampling adds complexity and a "but is the sample representative?" question that nobody is asking yet.

**Daedalus output.** Confirm full sweep for Gen 1. Note any threshold (e.g. "switch to sampling when EPHEMERA exceeds 50,000 nodes") as a deferred PHX ticket if Daedalus thinks it's worth recording.

### Q9 — `OneirosSettings` shape

**Question.** Hesiod's leaning across Q1–Q4 introduces a handful of tunable knobs. What's the shape of the `Settings` subgroup that holds them?

**Hesiod's proposal.**

```python
class OneirosSettings(BaseModel):
    tick_interval_s: float = Field(default=60.0, ge=0.01)
    promote_threshold: float = Field(default=0.7, ge=0.0, le=1.0)
    degrade_threshold: float = Field(default=0.25, ge=0.0, le=1.0)
    degrade_min_idle_days: float = Field(default=7.0, ge=0.0)
    connectivity_full_credit_edges: int = Field(default=20, ge=1)
    freshness_horizon_days: float = Field(default=30.0, ge=1.0)
    max_nodes_per_tick: int | None = Field(default=None, ge=1)
```

Exposed as `Settings.oneiros: OneirosSettings = Field(default_factory=OneirosSettings)`. Same pattern as `Settings.store` (introduced for batch_size in PR #24) and `Settings.report`.

**Daedalus output.** Confirm the field set or refine. Specifically: should `max_nodes_per_tick` exist at all in Gen 1 (where ≤2000 nodes makes it irrelevant), or is it the "I anticipate a future scale problem" anti-pattern that the §3.1 convention decisions warn against? Hesiod's leaning is to OMIT it for Gen 1 and let PHX-0046's ingest-side batch_size be the only "batch knob" the demo carries.

### Q10 — Iteration target: full layer or work-queue

**Question.** Each tick: does the worker iterate over the entire `EPHEMERA` layer (full sweep), or does it consume from a work-queue populated by `RelevanceTracker.bump()` and ingestion?

**Why it matters.** Full sweep is simple, deterministic, and matches Plan §4.3's prose ("for node in store.export_layer(EPHEMERA): ..."). Work-queue is more efficient at scale but adds queue-lifecycle questions (durable? in-memory? what happens at shutdown?).

**Hesiod's leaning.** Full sweep. The scale argument for a queue does not exist at ≤2000 nodes. The simplicity argument for a full sweep is durable across the entire Gen 1 surface.

**Daedalus output.** Confirm full sweep, OR propose work-queue + file a separate PHX ticket for queue infrastructure (Daedalus owns the architectural call here; Hesiod will not staff a queue without a Daedalus argument).
