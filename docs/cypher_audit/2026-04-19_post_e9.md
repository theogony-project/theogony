## Setup

- **2000 nodes** with the production `embedding_dim=384` (BGE-small) and varied `node_type` / `layer` / `manual_resolution_needed` / `confidence` so the WHERE filters in §1 and §5 hit non-trivial cardinalities
- **~4000 edges** (`LINKS_TO` and `REFERS_TO`, weights 0.5–0.95) connecting each node to two others (`(i + offset*7) mod N`) — sparse, multi-hop-traversable
- **All Plan §3.1a indexes present** — verified by the existing `tests/test_neo4j_store_live.py::TestSchemaBootstrap` checks

The harness is reproducible: `docker compose up -d neo4j && python scripts/cypher_audit.py`.

## §1 vector_search

```cypher
PROFILE
CALL db.index.vector.queryNodes('knowledge_node_embedding', 20, $embedding)
YIELD node, score
WHERE node.layer = $layer
  AND node.node_type IN $types
  AND node.confidence >= $min_conf
RETURN node.id AS id, score
```

- Records returned: **7**
- Total db hits: **53**
- db hits per record: **7.6**
- Top operators (descending db hits):
  - `Filter   node.layer = $layer AND node.confidence >= $min_conf AND node.node_type IN $types` — 46 db hits
  - `Projection   node.id AS id` — 7 db hits
  - `ProcedureCall   db.index.vector.queryNodes` — 0 db hits (HNSW handles it)
- Indexes: HNSW vector index served by the `db.index.vector.queryNodes` procedure (does not appear in the operator tree's "Index" column because it is a procedure call rather than a scan).

**Verdict: Accept.** The HNSW does the right thing — top-20 cosine-nearest are returned with zero db hits charged to the operator, all the work is inside the `ProcedureCall`. The post-filter `WHERE` runs over those 20 candidates and costs ~46 db hits total, an acceptable price for the structural filter.

**Known caveat (documented for future PHX, not addressed here):** Neo4j 5.18 does not support composite indexes that combine an HNSW vector index with property filters. If a query asks "top-k EPHEMERA persons by similarity" and *all* top-k candidates happen to be MNEME organisations, the WHERE will eat them and the result is empty even though closer EPHEMERA-person matches exist further down the cosine ranking. For the Gen 1 demo cardinality (~10⁴ nodes / k=10–20) this is not perceptible; in Gen 2 it could matter and a `vector_search_with_filter_pushdown` PHX would address it then.

## §2 traverse

```cypher
PROFILE
MATCH path = (start:KnowledgeNode {id: $start_id})
              -[r:RELATION*1..3]->(other:KnowledgeNode)
WHERE all(rel IN r WHERE rel.weight >= $min_weight
                   AND rel.relation_type IN $rel_types)
RETURN path
LIMIT 50
```

- Records returned: **3**
- Total db hits: **293**
- db hits per record: **97.7**
- Top operators:
  - `ProduceResults   path` — 267 db hits
  - `VarLengthExpand(All)   p = (start)-[r:RELATION*..3]->(other) WHERE …` — 21 db hits
  - `Filter   other:KnowledgeNode` — 3 db hits
  - `NodeUniqueIndexSeek   UNIQUE start:KnowledgeNode(id) WHERE id = $start_id` — 2 db hits
- Indexes: `knowledge_node_id_unique` (constraint-backed seek for the start node).

**Verdict: Accept.** The 267 db hits in `ProduceResults` are the cost of materialising 3 path objects (each containing nodes + relationships + their properties — including the 384-dim embedding on each touched node). The `VarLengthExpand` itself is cheap (21 db hits for ≤3-hop traversal across ~4000 edges). `relation_relation_type` and `relation_weight` range indexes (Plan §3.1a) cannot be used inside `VarLengthExpand` — Neo4j applies their predicates per-step but needs to walk every candidate relationship; range-index pushdown for variable-length relationship matches is a 5.x roadmap item, not Gen 1.

**Optimisation deferred to PHX-0042-followup if a reader complains:** strip the embedding from `path`-returned nodes via `[n IN nodes(path) | n {.id, .label}]` to drop the materialisation cost ~10x. Today the caller (`MultiHopRetriever`) discards the path's intermediate-node embeddings anyway — but that is its responsibility, not the Cypher's.

## §3 get_neighborhood

```cypher
PROFILE
MATCH (start:KnowledgeNode {id: $node_id})
OPTIONAL MATCH (start)-[r:RELATION*1..1]-(other:KnowledgeNode)
WHERE r IS NULL OR all(rel IN r WHERE rel.weight >= $min_weight)
WITH start, collect(DISTINCT other) AS others, collect(r) AS rel_lists
RETURN start.id AS start_id, [n IN others WHERE n IS NOT NULL | n.id] AS others
```

- Records returned: **1**
- Total db hits: **20**
- db hits per record: **20.0**
- Top operators:
  - `Filter   (r IS NULL OR all(rel IN r WHERE rel.weight >= $min_weight)) AND other:KnowledgeNode` — 8 db hits
  - `Projection   cache[start.id] AS start_id, [n IN others WHERE n IS NOT NULL | n.id] AS others` — 5 db hits
  - `VarLengthExpand(All)   (start)-[r:RELATION]-(other)` — 5 db hits
  - `NodeUniqueIndexSeek   UNIQUE start:KnowledgeNode(id) WHERE id = $node_id, cache[start.id]` — 2 db hits
- Indexes: `knowledge_node_id_unique`.

**Verdict: Accept.** 20 db hits per neighbourhood lookup is fine — the start-node seek is constant-time, the depth-1 expansion touches the small per-node fan-out (~2 edges in the fixture, ~2-5 in production text), and the EagerAggregation collapses results without materialising paths.

**This is the path PHX-0050 makes irrelevant for the assembler hot loop.** PHX-0050's `get_edges_among(node_ids)` collapses 10 of these calls into 1, replacing 200 db hits + 10 round-trips with ~20-40 db hits + 1 round-trip. The Cypher itself is OK; the *call pattern* is the problem the next commit fixes.

## §4 multi_hop_search seed (vector-only path)

The store's `multi_hop_search` runs the vector seed via `vector_search`, then issues per-seed `traverse` calls client-side. PROFILE'd here in its vector-seed-only form (the traverse part is already covered by §2):

```cypher
PROFILE
CALL db.index.vector.queryNodes('knowledge_node_embedding', 10, $embedding)
YIELD node, score
RETURN node.id AS id, score
```

- Records returned: **10**
- Total db hits: **10**
- db hits per record: **1.0**
- Top operators:
  - `Projection   node.id AS id` — 10 db hits (one per returned node, reading `id`)
  - `ProcedureCall   db.index.vector.queryNodes` — 0 db hits (HNSW)

**Verdict: OK.** The HNSW index does its job. `multi_hop_search`'s overall cost is dominated by the per-seed `traverse` calls (§2), each of which is bounded; the seed itself is essentially free.

## §5 list_pending_resolution

```cypher
PROFILE
MATCH (n:KnowledgeNode {manual_resolution_needed: true})
RETURN n.id AS id, n.label AS label
ORDER BY n.created_at DESC
LIMIT 20
```

- Records returned: **20**
- Total db hits: **121**
- db hits per record: **6.0**
- Top operators:
  - `NodeIndexSeek   RANGE INDEX n:KnowledgeNode(manual_resolution_needed) WHERE manual_resolution_needed = true` — 41 db hits
  - `CacheProperties   cache[n.label], cache[n.id]` — 40 db hits
  - `Projection   n.created_at AS n.created_at` — 40 db hits
  - `Top   n.created_at DESC LIMIT 20` — 0 db hits
- Indexes: `knowledge_node_manual_resolution` (Plan §3.1a range index) — exactly the path the schema anticipated.

**Verdict: OK.** The Plan §3.1a `manual_resolution_needed` range index does its job — `NodeIndexSeek` jumps straight to the candidate set; the rest is property-read cost (one `created_at`, `label`, `id` per row).

## Cross-cutting observations

1. **No path missed an index.** Every WHERE clause that references a Plan §3.1a indexed property hits the right index. The schema-bootstrap discipline from PR #18 (E7) was correct; nothing to add for Gen 1.

2. **No path exceeds the "obvious budget"** of 1000 db hits / record. The closest is `traverse` at 97.7 — and that is dominated by the cost of materialising path objects with the 384-dim embedding payload, not by traversal inefficiency.

3. **PHX-0050 is needed and well-scoped.** The audit confirms `get_neighborhood` is cheap *per call*; the assembler-hot-path problem is the *N+1 call pattern*, which PHX-0050 (`get_edges_among` bulk Cypher) is the right surface for. We ship it in this PR's next commit.

4. **PHX-0046 batch UNWIND was the right call.** §1–§5 are read paths; the *write* paths (single `upsert_node` / `upsert_edge` × N) were the actual hot spot for the IngestionPipeline, and PR commit `chore/post-e9-production-readiness@phx-0046` already addressed those (~10× speedup in `tests/test_neo4j_perf_smoke.py`).

5. **No PHX-0042-followup tickets needed today.** The two future-direction notes (HNSW + filter pushdown in §1; path-materialisation cost in §2) are documented inline; neither is on the Gen 1 demo critical path. File only when a real consumer complains.
